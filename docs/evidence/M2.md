## Oracle discrepancies discovered and documented (test-first discipline in action)

- **D-1 (`vec<defined>` unsupported + silent misalignment):** the chainstack `IDLParser` cannot decode `TradeEvent.shareholders` (vec of defined type) and — on failure — `continue`s **without advancing its decode offset**. Consequence: every oracle field AFTER `shareholders` (quote_mint…holder_rewards) is decoded from the shareholders bytes — misaligned garbage (observed literal `quote_mint='1111'`). Our Rust decoder handles the vec correctly per IDL (unit-tested roundtrip). Comparator excludes oracle post-shareholder fields (counted: 468 exclusions incl. D-2); Rust's trailing fields are validated by the aligned rows + unit tests. Chainstack production impact: its trader consumes reserves from account fetches, not those event fields — but any consumer trusting oracle post-shareholder fields would be poisoned. Recorded here as the canonical example of "oracle is subset truth, not gospel".
- **D-2 (EOF artifact synthesis):** on truncated (old-format) events the same continue-without-advance loop synthesizes empty-string values for some post-EOF fields (e.g. `quote_mint=''`). Comparator excludes empty-string artifacts on rows flagged truncated; Rust marks `is_truncated()` and omits undecoded fields.
- **Prefix tolerance semantics:** the oracle decodes ANY field-boundary prefix (a 14-field CreateEvent decodes with 14 fields). Rust mirrors this via `decoded_fields` counts — divergence from my first strict implementation was caught by the differential harness itself and fixed (three iterations recorded in session log).
